# game-development.md — Velocity-3D: Comparative Research & Build-Guidance Report

## TL;DR
- **Velocity-3D's core tech choice (TypeScript + HTML5 Canvas 2D + Vite + Web Audio API + Capacitor) is sound and well-matched to a Pole Position/OutRun scanline pseudo-3D renderer at 60fps** — the canonical reference engine (Jake Gordon's javascript-racer, built on Lou's Pseudo 3D Page) uses exactly this Canvas 2D segment-projection approach and reports "60fps at high res" in modern desktop browsers; the main risk area is mobile Safari/WKWebView, where a Canvas 2D fallback or a lightweight WebGL sprite-blitter should be planned.
- **Commercial retro racers converge on a proven feature set Velocity-3D should match:** OutRun's five-stage branching pyramid (15 scenes), Slipstream/80's Overdrive-style post-race money → engine/tyre/handling upgrades, ~15–30 tracks, three difficulty tiers, and "authentic retro look at a stable 60fps." Velocity-3D's spec already aligns; the gaps to close are a formal upgrade economy and a scalable track-authoring pipeline.
- **The desktop-first control scheme should be WASD (W=gas / S=brake vertically stacked, A/D steer), arrows as a mirror alternate, plus analog mouse steering (horizontal mouse-X → steering angle with a small deadzone and tunable sensitivity); iOS follows with a touch overlay + DeviceMotion tilt steering (requires a user-gesture `requestPermission()` call) and haptics via the `@capacitor/haptics` plugin (UIFeedbackGenerator presets; true CoreHaptics needs a custom native plugin).**

## Key Findings

### 1. Where Velocity-3D sits vs open-source engines
- **Jake Gordon's javascript-racer (jakesgordon.com, MIT)** is the definitive HTML5/Canvas 2D reference and is a direct implementation of Lou's "Realistic Hills Using 3D-Projected Segments" approach. Its architecture is the one Velocity-3D should build on: the road is an **array of segments**, each with `p1`/`p2` world→camera→screen projected points, a `curve` value, a `y` (hill) coordinate, a `sprites[]` array (roadside billboards/trees with a normalized `offset` from -1 to +1), and a `cars[]` array. Rendering is a two-phase loop: **front-to-back for the road** (with a `maxy` clip so hills occlude far segments — a cheap alternative to a full painter's algorithm) and **back-to-front for sprites/cars** (true painter's algorithm, since sprites overlap). Curves are faked by offsetting `cameraX` progressively per segment, not by computing real x-geometry. Gordon is explicit that if you needed real 3D geometry "we would be better off using WebGL… but that's not really what this project is about."
- Gordon's own caveat: the code is a **tech demo with global variables**, not production structure. He notes a real game needs "a road editor of some kind for visually creating a map with hills and curves." Velocity-3D's TypeScript modular architecture is the correct upgrade path.
- **Lou's Pseudo 3D Page (extentofthejam.com)** is the theory source: it explains that with just arithmetic you can reach "the level of detail seen in games like Pole Position or the first OutRun," and describes the segmented-road system where 3D-projected segments "always start and end on a specific scanline," rendered by scrolling the road graphic — the scanline aesthetic the user wants.
- **Cannonball (github djyt/cannonball, and forks bni/, J1mbo/cannonball-se)** is a different beast: a C++/SDL2 re-implementation of the actual OutRun 68000/Z80 arcade code, requiring the original ROMs. It uses OpenGL/OpenGLES/SDL2 for rendering and delivers "smoother 60fps gameplay," widescreen, force feedback, and **custom track support via the LayOut editor**. It's not a code base to port to TypeScript, but it is the gold-standard behavioral reference for OutRun-faithful physics, AI traffic, and the branching-stage structure, and LayOut demonstrates the value of a dedicated track editor. J1mbo/cannonball-se additionally shows how a CRT look is done at the GPU level (NTSC filter, shadow-mask, curvature, vignette via a 2-stage video filter).
- **Other ports worth studying:** ssusnic/Pseudo-3d-Racer and jamessimo/Phaser3-Road both re-implement the Gordon/Code-inComplete approach in Phaser, confirming the segment model ports cleanly to modern JS frameworks.

### 2. Commercial retro-racer benchmarking
- **Horizon Chase Turbo** — 12 total upgrades applied via choices during the campaign (per-run choice of speed/acceleration/steering/nitro/fuel); ~20 cars unlocked through progression; World Tour spans multiple locations each with several races plus an upgrade race; blue-coin collection for "Super Trophy"; Endurance modes of 12/36/109 races; three difficulty levels. Upgrades were historically garage-wide.
- **Horizon Chase 2** — shifts to **per-car** XP: race the same car to level it, then spend upgrade tokens. Per the Analog Stick Gaming review, "you'll be able to upgrade your car's performance in several key areas; Suspension, Air Intake, Differentials, Gearbox, and Nitro… These categories affect Top Speed, Acceleration, Handling, and your Nitro." Nintendo World Report highlights the design change: "Instead of unlocking one vehicle modification per country that applied to your entire garage, Horizon Chase 2 demands that you upgrade every car separately." World Tour spans ~5–6 countries (America, Brazil, Morocco, Italy, Thailand, Japan), each with multiple races; cosmetic customization (body kits, rims, paint) bought with coins; races are 2–3 minutes with 30–40s laps. Reviewers note it's "too easy" and rubber-banding is milder than the original — a difficulty-curve lesson for Velocity-3D.
- **Slipstream (Ansdor, custom pseudo-3D engine)** — the closest analog: "authentic pseudo-3D game engine with 2D graphics… just like the glory days," running at a smooth 60fps with texture filtering. Its official Steam store page lists "20 Different tracks, set on a variety of exotic locations all around the world… and beyond," 5 cars each with stats and color schemes (incl. an AE86 homage), OutRun-style **branching forks at the end of each stage**, and drift + slipstream mechanics. Crucially for Velocity-3D's economy, the Steam page describes "Grand Prix, a championship mode with five races back to back and money prizes used to upgrade your car!" It also has a 5-stage Grand Tour with branching paths and rewind (up to 5s), and later added mod tools + Steam Workshop.
- **80's Overdrive (Insane Code)** — career mode where you "unlock new races, buy new cars, and upgrade them." Per Gematsu quoting the developer, there are "Six retro supercars of the '80s such as Penetrator GT, Intruder Turbo, and De Loan. Players will be able to upgrade engine, chassis, and tires to improve top speed, acceleration, handling, and braking. Car can be also equipped with police radar and nitro boost… Eight unique visual themes… 18 synth/retrowave music scores." It ships a **built-in track generator** with shareable track codes, plus Time-Attack (OutRun mode) and police-chase career. This is the single best template for Velocity-3D's upgrade taxonomy and content-generation strategy.
- **Hotshot Racing (Sumo Digital, polygonal not scanline)** — 16 tracks across 4 themed locations / 4 Grand Prix, 8 drivers each with 4 cars (all-rounder + accel / top-speed / drift specialists), "silky smooth 60fps on every platform including Switch," three difficulty levels that scale speed + AI aggression. Reviewers wanted more/harder tracks — reinforcing the user's "many levels" priority. Note one player found 60fps "not… stable… starts to stutter when I chain drifts," a caution about overdraw.
- **art of rally (a more sim-leaning outlier)** — per the Pixel Die review (Feb 2021), "Career mode takes you through six groups of vehicles… showing off art of rally's 30 pre-made tracks, becoming 60 with the optional reversed starting points." (The current Steam store page now advertises Career mode "travelling across 91 stages" across Finland, Sardinia, Norway, Japan, Germany, Kenya and Indonesia.) Its handling model is more demanding than the OutRun lineage.
- **Verdict:** Velocity-3D's target set (retro look, 60fps, upgrades, many levels) is exactly the winning formula these titles share. The clearest opportunities are (a) a richer, persistent upgrade economy (Slipstream/80's Overdrive model) and (b) more tracks than the ~15–20 norm, achieved via the branching pyramid plus a data-driven authoring pipeline.

### 3. Tech-stack validation
- **Canvas 2D vs WebGL for a scanline pseudo-3D renderer:** The pseudo-3D road is drawn as a few hundred trapezoid/quad fills per frame plus a modest number of scaled sprite `drawImage` calls — well within Canvas 2D's budget. Benchmarks put Canvas 2D at roughly "1,000–3,000 simple draws per frame at 60fps on a mid-range laptop," while WebGL "sails past 50,000." A pseudo-3D racer at ~300 road segments drawn + a few dozen sprites sits comfortably in Canvas 2D's range. Real-world confirmation: Gordon's Canvas 2D racer runs "60fps at high res" in Firefox and Chrome with GPU canvas acceleration. Caveats that erode the Canvas budget: gradient fills, shadow blur, and per-frame allocations — all avoidable here.
- **Where Canvas 2D struggles:** it cannot cheaply do full-screen shader effects (CRT scanline/curvature, per-pixel color cycling). Cannonball-SE achieves NTSC filter / shadow-mask / curvature via shaders. If Velocity-3D wants an authentic CRT post-process, that is the one feature that argues for either a WebGL final-composite pass or PixiJS (WebGL with Canvas fallback).
- **Recommendation:** **Keep Canvas 2D as the primary renderer** for the road/sprite layer (it is the right call for this workload, matches the reference engines, and keeps the code simple and portable). Architect the renderer behind an interface so a **WebGL/PixiJS path can be swapped in** if (a) mobile Safari/WKWebView profiling shows Canvas 2D dropping frames, or (b) you want a GPU CRT post-processing shader. This is a low-regret hedge.
- **Mobile/WKWebView reality:** Gordon warned in 2012 that mobile browser performance was "pretty dismal"; that is far less true today, but WKWebView remains the risk surface. Capacitor uses WKWebView which benefits from JIT JavaScript (unavailable to React Native's JS on iOS), and the official Capacitor "Games" guide states: "With broad support for WebGL and canvas rendering, developers can build high-performance game experiences on modern mobile devices." Known WKWebView pitfalls include historical iOS 15 GPU-process canvas crashes and memory pressure with large textures — mitigate with texture atlases, capped canvas resolution, and device testing.
- **Vite** is the correct modern build tool (fast HMR, ES modules, TS-native). **Web Audio API** is validated for game audio: it has a "low-latency precise-timing model" essential for engine/collision SFX; best practice is a **hybrid** — HTMLAudioElement/streamed for background music, Web Audio buffers for low-latency SFX — with all SFX **preloaded**, routed through separate gain nodes for music vs SFX, and the AudioContext **resumed on a user gesture** (browser autoplay policy). Consider howler.js if you want cross-browser abstraction, but raw Web Audio is fine.

### 4. Rendering approach for "retro look at a stable 60fps"
- Use Lou/Gordon's **3D-projected segment** model: a fixed internal resolution (e.g., 320×240 or 480×270 logical, integer-scaled to the window) to lock the chunky retro look and bound fill cost.
- Render at a **fixed logical framebuffer** then nearest-neighbor upscale — this both nails the Pole Position pixel aesthetic and decouples fill cost from display resolution.
- **Decouple simulation from rendering:** run physics at a fixed timestep (e.g., 60Hz accumulator) so behavior is deterministic and frame-rate independent; interpolate rendering. This is essential for stable feel and for vitest-testable physics.
- Draw order per frame: sky/background parallax → road segments front-to-back with `maxy` hill clipping → roadside sprites and traffic back-to-front → player car → HUD.
- Optional authentic CRT: reserve a WebGL/PixiJS post pass (scanlines, slight curvature, bloom), as demonstrated by Cannonball-SE, as a Phase-later enhancement, off by default on mobile for perf.

### 5. Car-upgrade / post-race economy design (proposed)
Synthesizing 80's Overdrive, Slipstream, and Horizon Chase 2 plus F2P economy theory:
- **Currency:** a single soft currency ("Credits") earned per race, scaled by finishing position and bonus objectives (clean laps, drift/near-miss bonuses, collectibles akin to blue coins). Keep it a **premium-free, skill-earned** economy (no loot boxes) to preserve arcade purity.
- **Upgrade categories (map directly to physics params) — modeled on 80's Overdrive's "engine, chassis, and tires → top speed, acceleration, handling, and braking":**
  - **Engine / Top Speed** → raises `maxSpeed`.
  - **Turbo / Acceleration** → raises `accel` curve.
  - **Tyres / Grip (Handling)** → raises `centrifugal`/off-road-penalty resistance and cornering `maxSteer`.
  - **Brakes** → raises `braking` deceleration.
  - **Nitro** (optional arcade flavor) → temporary speed boost, capacity upgradable.
- **Upgrade model:** **persistent, tiered** per-car upgrades (3–5 tiers each), bought after races in a Garage screen. Persistent (not consumable) keeps it satisfying for an arcade audience; escalating costs per tier provide the long tail. Follow the balance rule "upgrade cost should feel proportional to the upgrade's impact," and design earn rate around a casual "once a day, 20 minutes" player while capping runaway power-players.
- **Progression loop:** race → earn Credits + objective bonuses → buy upgrades/new cars → unlock harder stages → repeat. Give each session a **visible advance toward the next upgrade**. Offer multiple cars with distinct stat archetypes (accel vs top-speed vs handling), mirroring Hotshot's four-car philosophy so different tracks favor different builds.
- **Anti-frustration:** avoid the rubber-banding excesses reviewers criticized in Horizon Chase; consider a mild catch-up on Credits (not on race position) so weaker players still progress.

### 6. Track / level content strategy for "many levels"
- **Data format:** serialize tracks as JSON — an array of **road-piece descriptors** (e.g., `{ curve, length, hill, sprites[], cars?, roadType }`) compiled at load into the per-segment array. This is the Gordon model plus 80's Overdrive/LayOut's proven track-code idea. Keep it human-readable (JSON/TOML) so tracks are hand-authorable and diffable.
- **Authoring:** build a **track editor** early (Gordon and Cannonball's LayOut both stress this). Hand-authored tracks give the "strong, well-designed tracks" the user wants; a **procedural generator** (seeded) can multiply content for endless/bonus modes, following the segment-append pattern (add straights/arcs, vary length/angle, place sprites) — the same technique 80's Overdrive exposes to players via its track generator. Blend both: hand-authored "hero" stages + procedural filler/endurance.
- **Branching pyramid (TX-1 / OutRun):** implement the **five-stage, expanding-fork structure**: Stage 1 → 2 stage-2 scenes → up to 5 stage-5 scenes, **15 unique scenes, 25 possible five-stage routes** (corroborated across GameFAQs, Giant Bomb, StrategyWiki and Hardcore Gaming 101), all leading to multiple endings. TX-1 (1983) pioneered the branch; OutRun (1986) popularized it. This is the single highest-leverage way to deliver "many levels" with replayability from a modest scene count. Support **3-way forks** (left/straight/right), as TX-1 did, for extra variety.
- **Scale target:** aim to exceed the retro-racer norm — e.g., 15 hand-authored scenes in the primary pyramid (25 route permutations), plus additional themed pyramids/cups and a procedural endurance mode, comfortably delivering "many levels."

### 7. Desktop control scheme (primary platform)
- **Keyboard — WASD (default):** **W = accelerate, S = brake**, stacked vertically so the same finger rocks between throttle and brake (mirrors a pedal's heel-toe mental model and keeps gas/brake "close together" as required); **A = steer left, D = steer right**. This is the de-facto standard cluster; WASD is preferred for shared/online builds because it's layout-agnostic on English keyboards. Space = handbrake/drift; Left-Shift / Left-Ctrl or `E`/`Q` for gear-up/down or nitro (keep secondary keys within the left-hand's reach; avoid numpad, which may be absent/NumLock-dependent).
- **Keyboard — Arrows (alternate):** Up = gas, Down = brake, Left/Right = steer, mirroring WASD so left- or right-handed players can pick either; keep a symmetric secondary cluster (e.g., `.`/`/` or RCtrl/RShift) for drift/gears.
- **Rebinding:** ship a remap screen — the recurring itch.io developer lesson is "the only way to make every player happy… is to let them decide their own mapping."
- **Analog mouse steering (option):** map **horizontal mouse position/movement (mouse-X) to steering angle**. Two proven approaches: (a) **absolute** — screen-x relative to center maps to steer -1..+1; (b) **relative/velocity** — accumulate mouseX delta into a steering value that self-centers. Apply a **small deadzone** near center (to avoid jitter/drift) and a **tunable sensitivity**; a mild **exponential/S-curve** gives fine center control with full lock at the edges (racing-game convention: linear for consistency, exponential for precision). Real-world tuning data from sim racers: ~400 DPI mice with mid-range in-game sensitivity give smooth mouse steering; a persistent center-deadzone that ignores tiny movements prevents unwanted micro-steer. Mouse also drives all menu/HUD/Garage navigation.
- **Gamepad:** free bonus — left stick or triggers (RT gas / LT brake) map naturally; support it since the physics is already analog-ready.

### 8. iOS / iPad controls (Phase 2 platform)
- **Touch overlay:** on-screen left/right steer zones + gas/brake buttons, or a "tap-left-half / tap-right-half to steer, auto-accelerate" arcade default; keep buttons large and thumb-reachable.
- **Gyro / accelerometer tilt steering:** use `DeviceMotionEvent`/`DeviceOrientationEvent`. On iOS 13+ you **must call `DeviceMotionEvent.requestPermission()` from a user gesture** (e.g., a "Tap to enable tilt steering" button). Per MDN: "This method requires transient activation, meaning that it must be triggered by a UI event such as a button click… A Promise that resolves with a string which is either 'granted' or 'denied'… This feature is available only in secure contexts (HTTPS)." **Feature-detect** (`typeof DeviceMotionEvent.requestPermission === 'function'`) because non-iOS fires motion events without a prompt. **WKWebView caveat:** behavior is version/config-dependent — WebKit's own bug tracker states WKWebView has direct access without permission, yet many Capacitor apps report needing to call `requestPermission()` from a gesture; permission may not persist across app launches, so re-request on launch. Map tilt (beta/gamma) to steering with a calibratable neutral angle (a natural hold, not flat) and a deadzone.
- **Haptics:** use the **official `@capacitor/haptics` plugin** — methods `impact({style: Heavy|Medium|Light})`, `notification({type: Success|Warning|Error})`, `vibrate({duration})`, and `selectionStart/Changed/End()`. On iOS these wrap **UIKit's UIFeedbackGenerator** (UIImpactFeedbackGenerator / UINotificationFeedbackGenerator / UISelectionFeedbackGenerator) — Taptic Engine presets, **not** CoreHaptics. Per the Capacitor docs, on devices without a Taptic Engine "the API calls will resolve without performing any action." **CoreHaptics limitation:** the plugin exposes no custom intensity/sharpness curves, continuous events, or `.ahap` patterns — advanced/continuous haptics (e.g., engine-rev rumble) require a **custom Capacitor Swift plugin wrapping `CHHapticEngine`** (gated on `CHHapticEngine.capabilitiesForHardware().supportsHaptics`). Recommend shipping v1 with preset impacts (collision = heavy impact, gear/UI = selection) and treating CoreHaptics as an optional enhancement.
- **Capacitor deployment:** iOS 15+ target, Xcode 26+ for current Capacitor; uses WKWebView; test on real devices for canvas memory/perf; use texture atlases and capped resolution.

### 9. Claude Code build roadmap
- **CLAUDE.md** should be a **short, always-true "router,"** not a novel — prune ruthlessly. Contents: project one-liner and goals (retro pseudo-3D racer, 60fps, desktop-first then iOS); tech stack + versions (TS, Vite, Canvas 2D renderer interface, Web Audio, Capacitor); architecture map (modules: `engine/` render+projection, `physics/` fixed-timestep sim, `track/` loader+editor+data schema, `economy/` upgrades+save, `input/` keyboard/mouse/touch/gyro abstraction, `audio/`, `ui/`); coding conventions; **test command** (`vitest`) and build commands; the phased roadmap; and hard rules ("physics must be deterministic/fixed-timestep and unit-tested"; "renderer stays behind the RenderBackend interface"). Convert "must always happen" rules into hooks where possible.
- **Plan mode first:** use Claude Code's plan mode to explore and design before editing — "use plan mode before you let it edit." Keep an `active-plan.md` per feature/slug.
- **Subagent delegation:** fan out independent work — e.g., a subagent to research/scaffold the track editor, another to write the physics test suite — since "subagents run in separate context windows and report back summaries," keeping the main context clean. Use a reviewer subagent to check diffs against the plan ("report gaps, not style preferences").
- **Testing with vitest:** unit-test the pure logic — projection math, curve/hill interpolation, physics step (accel/brake/grip/centrifugal), economy (earn/cost curves, save/load), and track-JSON loader/validation. Keep rendering thin and logic pure so it's testable headlessly.
- **Phased development (building on the spec's existing roadmap):**
  1. **Phase 0 — Scaffold:** Vite + TS + vitest + CLAUDE.md; RenderBackend interface; fixed-timestep game loop.
  2. **Phase 1 — Straight road:** segment projection onto Canvas 2D (Gordon v1).
  3. **Phase 2 — Curves + hills:** cameraX offset curves; y-coordinate hills with `maxy` clipping (Gordon v2/v3).
  4. **Phase 3 — Sprites, traffic, collisions, HUD** (Gordon v4); fixed logical resolution + integer upscale.
  5. **Phase 4 — Physics feel + controls:** WASD (W/S throttle-brake), arrows alternate, analog mouse steering, gamepad; deterministic tuning.
  6. **Phase 5 — Track data + editor:** JSON schema, loader, hand-authored hero tracks, procedural generator.
  7. **Phase 6 — Branching pyramid + many levels:** 5-stage forks, 15 scenes / 25 routes, multiple endings, cups.
  8. **Phase 7 — Economy:** Credits, Garage, tiered upgrades mapped to physics, save system.
  9. **Phase 8 — Audio + juice:** Web Audio SFX + music, optional CRT shader.
  10. **Phase 9 — iOS via Capacitor:** touch overlay, gyro tilt (`requestPermission`), `@capacitor/haptics`, device perf pass, App Store.

## Details
Each numbered section in Key Findings maps to one of the eight research tasks and is written to be pasted directly into the project's `game-development.md`. The through-line: Velocity-3D's spec is architecturally correct and market-aligned; the work is to (1) formalize the segment-based renderer behind a swappable backend interface, (2) add a persistent upgrade economy, (3) build a JSON-driven track pipeline with an editor and a branching pyramid, (4) implement the WASD/arrows/mouse desktop controls first, then (5) layer iOS touch/gyro/haptics via Capacitor, all under a phased, test-driven Claude Code workflow.

## Recommendations
1. **Adopt Canvas 2D now, behind a `RenderBackend` interface.** Ship desktop on Canvas 2D. Threshold to switch a layer to WebGL/PixiJS: if WKWebView profiling on a target iPhone/iPad shows sustained frame time >16.6ms with the full road+traffic scene, or if you commit to a GPU CRT post-process. Until then, Canvas 2D is the lower-complexity, reference-proven choice.
2. **Lock the retro look with a fixed logical framebuffer (e.g., 480×270) + nearest-neighbor upscale, and a fixed-timestep sim.** This guarantees the Pole Position aesthetic and bounds fill cost — the two levers for stable 60fps.
3. **Build the track editor and JSON schema in Phase 5, before authoring bulk content.** Every reference engine author says the editor is what turns a tech demo into a game. Pair hand-authored hero stages with a seeded procedural generator for endurance modes.
4. **Implement the OutRun/TX-1 branching pyramid** as the backbone of "many levels": 15 scenes → 25 routes → multiple endings, plus additional cups; this maximizes content-per-asset.
5. **Ship the persistent, skill-earned upgrade economy** (Engine/Speed, Acceleration, Tyres/Grip, Brakes, Nitro) with escalating tiered costs, tuned for a 20-min/day casual player; no loot boxes. Multiple car archetypes so builds matter per track.
6. **Desktop controls:** default WASD with W=gas/S=brake stacked, A/D steer; arrows as full mirror alternate; analog mouse-X steering with center deadzone + tunable (exponential-option) sensitivity; full remap screen; gamepad support. Mouse also runs all menus/Garage.
7. **iOS in Phase 9:** touch overlay + gyro tilt (gesture-gated `requestPermission`, feature-detected, re-requested on launch) + `@capacitor/haptics` presets; defer a CoreHaptics custom plugin unless engine-rumble is a priority.
8. **Claude Code:** short router-style CLAUDE.md; plan mode before edits; subagents for research/editor/tests; vitest on all pure logic (projection, physics, economy, track loader); keep the spec's phased roadmap and extend it as above.
- **Benchmarks that change the plan:** sustained sub-60fps in WKWebView → introduce a WebGL sprite layer; playtest showing upgrades trivialize difficulty → flatten upgrade impact or steepen AI/track difficulty; players confused by branching → add a route-map screen (as OutRun shows the pyramid at the end).

## Caveats
- **Frame-rate claims are context-dependent.** Gordon's "60fps at high res" is desktop, GPU-accelerated, circa-2012 browsers; he explicitly did not optimize and called mobile "dismal" at the time. Modern mobile is far better but must be verified on real iOS hardware — treat 60fps on WKWebView as a goal to prove by profiling, not an assumption.
- **Hotshot Racing's 60fps was reported as occasionally unstable** by at least one player ("starts to stutter when I chain drifts") even in a polished commercial title — a reminder that overdraw and effects must be budgeted.
- **WKWebView DeviceMotion permission behavior is genuinely contested** across iOS versions and app configs (WebKit says no permission needed in WKWebView; many Capacitor devs report needing a gesture-triggered `requestPermission()`). Code defensively: feature-detect, try `requestPermission()`, fall back to attaching listeners directly, and re-check on each launch.
- **`@capacitor/haptics` uses UIFeedbackGenerator, not CoreHaptics** — inferred from the docs' explicit UIImpactFeedbackGenerator/UINotificationFeedbackGenerator mappings and the preset-only API surface; advanced patterns need a custom native plugin.
- **Some sources are secondary** (wikis, review sites, forum posts) for game feature counts; where possible these were corroborated across multiple outlets (e.g., OutRun's 15 scenes / 5 stages appears consistently across GameFAQs, Giant Bomb, StrategyWiki and Hardcore Gaming 101). art of rally's track count differs between the 2021 review era (30/60) and the current Steam page (91 stages) — cite per era.
- **Horizon Chase upgrade specifics** differ between Turbo (12 campaign-choice upgrades, historically garage-wide) and 2 (per-car XP: Suspension/Air Intake/Differentials/Gearbox/Nitro) — cite the correct title per claim.
- **Claude Code tooling** (skills, agent teams, plan mode, hooks) is evolving rapidly; verify current syntax against the official Claude Code docs at build time.
