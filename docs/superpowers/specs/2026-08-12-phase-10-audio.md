# Phase 10 — Audio (design spec)

> **Spec only.** This documents the design for a future implementation session. No code,
> no matching implementation plan, and no `src/audio/` files exist yet — greenfield.

Source spec for `plan.md` Phase 10 ("Audio & juice"). Scope: procedural engine audio, tire
squeal, hybrid music/SFX playback, and an optional CRT post pass. Follows this project's
established pattern of pure/testable logic decoupled from the render/audio edge (Hard rule 5:
zero external deps in the engine core — Web Audio is a browser-native API, so it's fine to
touch directly at the `audio/` edge, same footing as `net/supabase.ts`).

---

## 1. What already exists to drive this

`physics/Vehicle.ts` implements `PlayerState` (`types/engine.ts`) and already surfaces every
signal the audio engine needs per step, with no new physics work required:

- `speed` (world u/s — HUD converts to km/h) and `gear` (1 = Low, 2 = High, via `gearIdx`)
  → engine pitch.
- `skidding` (`isSkidding`, boolean) → tire squeal gate.
- `braking` (`lastBraking` — brake or handbrake held) → could gate a brake/skid-adjacent cue,
  though the spec's squeal trigger is skid state, not braking.

`main.ts` already runs a fixed-timestep physics loop (`physics/loop.ts`) and constructs
`Renderer`/`HUD` synchronously; whatever polls `PlayerState` for audio should follow the same
fire-and-forget-safe pattern `loadAtlases.ts` established (never block construction, never
throw on missing assets/permissions).

## 2. Engine audio — procedural, not sampled

Signal chain per the plan: `OscillatorNode` (sawtooth) → `BiquadFilterNode` (lowpass) →
`GainNode` → destination (routed through a dedicated SFX bus, §4).

- **Pitch:** `f_osc = f_base + (kmh / gearMaxKmh[gearIdx]) * f_range`, re-derived from `speed`
  and `gear` each step (or on a coarser tick — see §5 on allocation). `f_base = 40Hz` for low
  gear per the plan; `f_range` and the high-gear `f_base` need picking during implementation
  (not specified numerically anywhere in `plan.md`/the research doc — treat as a tuning
  constant in `constants.ts`, same pattern as `CENTRIFUGAL`/`STEER_MAX_WPS`).
  `gearMaxKmh` is already the natural per-gear speed cap (`physics/Vehicle.ts`), so a gear
  change reads as the expected pitch drop — no new state needed to detect a shift.
  **Note:** `PlayerState.gear` is a stubbed `1` per its own doc comment in `types/engine.ts` in
  earlier phases — confirm at implementation time that Phase 9's gear mechanic (`gearUp`/
  `gearDown` commands, seen in `Vehicle.step`) is what's live, not the old stub.
- **Filter:** `BiquadFilterNode` cutoff as a second function of RPM/speed (the plan specifies
  "cutoff = f(RPM)" without a formula) — gives the engine tone brightness at high RPM instead
  of a flat buzz.
- **One oscillator graph reused across the run**, not recreated per step — matches Hard rule 4
  (no per-frame allocation) applied to the audio graph: build the node graph once, update
  `.value` on the existing `AudioParam`s each tick via `setTargetAtTime` (avoids zipper noise
  from stepping `.value` directly) rather than tearing down/rebuilding nodes.

## 3. Tire squeal — filtered noise, gated by skid

- **Source:** a pre-generated noise buffer (`AudioBuffer` filled with white noise once, looped
  via `AudioBufferSourceNode`) rather than a `ScriptProcessorNode`/`AudioWorklet` — simpler,
  and avoids a real-time synthesis dependency for a short-lived cue.
- **Shaping:** high-pass `BiquadFilterNode` at ~1200Hz per the plan.
- **Gate:** `GainNode` driven by `Vehicle.skidding` (already boolean, already surfaced) —
  gain 0 → target on skid start, target → 0 on skid end, eased via `setTargetAtTime` to avoid
  a click. "Gain by skid magnitude" (plan wording) implies a continuous intensity, not just
  on/off; `Vehicle` doesn't currently expose a skid *magnitude* (only the boolean + internal
  `skidDir`/`recoverySteps`) — decide at implementation time whether to derive an approximate
  magnitude from `recoverySteps` progress or widen `PlayerState` with a real one. Prefer the
  narrower option (approximate from existing state) unless it reads badly, per this project's
  pattern of not widening shared interfaces speculatively (Spec C only widened `PlayerState`
  when the brake-light overlay had no other signal to use).

## 4. Hybrid playback: streamed music, preloaded SFX

- **Music:** `<audio>` element (or `MediaElementAudioSourceNode`) for streaming — avoids
  buffering a full track into memory, matches the "hybrid" directive and the WKWebView-memory
  caution already flagged for Phase 11.
- **SFX:** short one-shots (collision thud, overtake chime if any, UI confirm) preloaded as
  `AudioBuffer`s via `fetch` + `decodeAudioData`, played through `AudioBufferSourceNode`
  instances — same "never block construction" discipline as `loadAtlases.ts`: kick off loads
  fire-and-forget, degrade to silence if a buffer isn't ready yet rather than throwing.
- **Bus routing:** separate `GainNode` buses for music and SFX (each feeding
  `AudioContext.destination`), so a future settings screen can offer independent volume
  sliders without touching playback code — mirrors how `net/` modules stay swappable behind
  `SaveBackend`.
- **Autoplay policy:** `AudioContext` starts `suspended` in every browser that matters here;
  `resume()` must be called from an existing user-gesture handler. The codebase already has
  gesture handlers wired (`canvas.addEventListener('click', ...)` for pointer lock, keydown
  handlers for restart/menus in `main.ts`) — reuse one of those rather than adding a new
  "click to start audio" prompt, unless testing shows the existing gestures fire too late
  (e.g. after the race has already started making sound cues relevant).

## 5. Where this plugs into the game loop

- `audio/SoundEngine.ts` should own its own small "audio step" function, called from `main.ts`
  once per rendered frame (not once per fixed physics step — audio doesn't need 60Hz-exact
  determinism the way physics does; `requestAnimationFrame` cadence is fine and avoids
  re-touching `physics/loop.ts`, which Hard rule 3 keeps deterministic and decoupled from
  everything else).
- Reads `PlayerState` (already computed for rendering) — no new coupling between physics and
  audio beyond the existing read-only interface.
- Collision cues: `engine/Collision.ts`'s new `ContactLatch.enter()` (landed this session,
  `fix(physics)` commit on `phase-9-modular-economy`) already reports "true on the first step
  of a new contact" — the natural hook for a one-shot collision SFX trigger, avoiding the same
  per-step-repeat bug that motivated `ContactLatch` for the physics response.

## 6. CRT post pass — optional, separable

- Explicitly "off by default on mobile" per the plan. Scanlines/curvature/bloom via a
  WebGL/PixiJS pass, which is a materially different technical track from everything else in
  this spec (Web Audio vs. rendering) and from Hard rule 1 (segment model, no WebGL geometry —
  though a post-process pass over the existing Canvas2D output is not the same thing as 3D
  geometry, worth confirming that distinction holds before implementation).
- **Recommend splitting this into its own follow-up spec/implementation pass**, sequenced
  after the audio work lands — it has no dependency on `SoundEngine.ts` and bundling both
  under one "Phase 10" implementation risks a much larger, harder-to-review diff than the
  audio half alone.

## 7. Testing (vitest)

Following the project's pattern of testing pure logic and treating browser-API edges as thin,
manually-verified wrappers (same split as `net/supabase.ts` vs. `net/leaderboard.ts`):

- **Pure and testable:** pitch/filter-cutoff formulas as standalone functions of
  `{speed, gear, gearMaxKmh}` → `{frequency, cutoff}`, independent of any `AudioNode`. Skid
  gain/magnitude derivation as a pure function of `PlayerState`. Bus-gain math if any
  (e.g. ducking music under SFX, if that's wanted — not in the plan's scope, flag only if it
  comes up).
- **Thin/manual at the edge:** actual `AudioContext`/node construction, `resume()` gesture
  wiring, buffer loading — mirrors how `loadAtlases.ts`/`loadBackdrops.ts` keep the
  fetch-and-decode edge separate from the pure frame-index math they feed.
- **Regression guard:** an `AudioContext`-construction failure (unsupported browser, gesture
  never fires) must not throw or block gameplay — same "never rejects" discipline as
  `engine/loadAtlases.ts`. Worth a test that the game loop runs to completion with a null/stub
  audio backend, same shape as the existing Supabase null-client tests.

## 8. Done-when

Engine pitch audibly tracks speed and gear across a full gear range; tire squeal is audible
exactly while `skidding` is true and silent otherwise; music streams without blocking asset
load; SFX fire with no perceptible latency; the game is fully playable with audio blocked/
unsupported (no thrown errors, no silent hang). CRT pass, if pursued in the same phase, is
verified off by default on a mobile viewport.

## Open questions for the implementation session

1. Exact `f_base`/`f_range`/high-gear pitch constants — not numerically specified anywhere
   upstream; needs ear-tuning against a real drive, same as `CENTRIFUGAL` was this session.
2. Whether skid "magnitude" needs a real `PlayerState` field or an approximation from existing
   internal state is good enough — try the approximation first.
3. Whether the CRT pass belongs in this phase at all, or should be pushed to Phase 11 (web
   polish) where the profiling-pass prerequisite already lives — recommend the latter (§6).
